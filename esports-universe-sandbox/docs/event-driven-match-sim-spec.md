# Esports Universe Sandbox — 事件驅動式 LoL 比賽模擬引擎

## 一、專案背景

專案名稱：Esports Universe Sandbox

主要技術：
- Angular
- TypeScript
- 現有專案資料模型與服務架構

目前模擬引擎位置：

`src/app/shared/sim/`

目前已經具備：
- 選手六維能力
- 教練能力
- 隊伍風格推導
- 選手相性與團隊整合
- BP 模擬
- 前期、中期、後期戰力計算
- 風格克制與隨機因素
- BO1、BO3、BO5 系列賽模擬
- MatchReport 比賽報告
- 例行賽、季後賽、升降賽、MSI、生死戰等自動模擬接線

目前的問題：

現有模擬主要透過四個階段的戰力差距，使用 logistic 勝率決定單局勝負。

雖然已經考慮選手能力、隊伍風格與教練，但還沒有真正模擬出一場 LoL 比賽的過程。

目前經濟折線圖甚至會出現：
- 比賽開始約 1 分鐘就產生數百經濟差。
- 不合理的早期防禦塔摧毀事件。
- 經濟曲線沒有明確事件來源。
- 經濟、擊殺、物件及比賽時間軸之間缺乏一致性。

本次希望將系統逐步發展為：

**以比賽事件為核心，透過選手、隊伍、教練、BP、戰術與隨機因素共同決定比賽發展的事件驅動模擬引擎。**

# 二、最重要的設計原則

## 2.1 比賽事件是唯一資料來源

必須遵守：

**比賽不是先決定勝負，再隨機生成經濟、KDA 和比賽事件。**

正確流程：

1. 根據雙方陣容、能力、隊伍特色、教練及 BP，決定雙方比賽傾向。
2. 模擬比賽中的行動與決策。
3. 根據條件判定是否發生事件。
4. 事件產生實際效果。
5. 更新選手數據、隊伍數據及經濟。
6. 記錄比賽時間軸。
7. 根據事件與比賽狀態持續推進比賽。
8. 最後根據實際比賽結果決定勝負。

經濟曲線、KDA、傷害、物件控制、比賽時間軸與 MatchReport 必須使用同一場比賽的資料。

禁止各自使用不同的隨機邏輯生成結果。

## 2.2 不追求平滑，追求合理

真實 LoL 比賽可以有激烈的經濟波動。

例如：
- 開局野區埋伏造成 First Blood。
- 前期 Gank 連續成功，迅速拉開經濟差距。
- 一方拿到小龍，另一方換取防禦塔。
- 中期團戰造成多人死亡，經濟瞬間改變。
- 巴龍團戰失敗，原本領先的隊伍被反超。
- 後期抓到關鍵選手，直接結束比賽。

因此，不要為了讓曲線好看而強制平滑。

但每一次明顯的經濟變化都必須有合理原因。

例如，1 分鐘領先 500 經濟並非絕對禁止，但必須能從首殺、助攻或其他實際事件解釋來源。

## 2.3 OVR 不得成為勝率主公式

保留原本的設計理念：

- 選手能力決定個人執行能力。
- 隊伍特色決定戰術傾向。
- 教練影響 BP、戰術與臨場調整。
- 陣容組合決定對線與團隊配合。
- 比賽狀態影響雙方決策。
- 隨機因素產生發揮差異與爆冷機會。

不得退回單純比較隊伍 OVR 的舊系統。

# 三、選手能力系統

沿用目前既有選手資料，不要任意修改既有 Schema。

能力尺規為 0～120。

目前六維能力：

| 能力 | 英文欄位 | 主要用途 |
|---|---|---|
| 對線 | laning | 對線壓制、補刀、換血 |
| 操作 | mechanics | 技能命中、操作執行、團戰操作 |
| 團戰 | teamfighting | 團戰輸出、站位、開戰與反打 |
| 意識 | gameSense | 地圖判斷、資源決策、視野與支援 |
| 穩定性 | consistency | 發揮穩定程度、失誤控制 |
| 適應力 | adaptability | BP 適應、戰術調整、臨場應變 |

其他既有資料：
- current
- potential
- growthRate
- form
- position

單場模擬只使用 current、form 等當前比賽相關資料。

potential、growthRate 保留給長期球員成長系統，不直接影響單場比賽。

## 3.1 選手能力必須反映在實際事件

例如：

高對線能力：
- 更容易建立線上補刀差。
- 更容易取得線權。
- 換血與對線壓制表現較好。

高操作能力：
- 技能命中率較高。
- 單挑與團戰操作表現較好。
- 關鍵技能執行失誤較少。

高意識：
- 更容易掌握敵方打野位置。
- 更容易判斷支援與撤退時機。
- 更容易參與物件控制與地圖決策。

高團戰能力：
- 團戰輸出效率較高。
- 更容易在團戰中找到輸出位置。
- 開戰、反打及集火執行更好。

高穩定性：
- 降低不必要失誤。
- 減少發揮波動。
- 壓力下較不容易出現重大失誤。

高適應力：
- 更容易應對不同對線組合。
- 能夠調整打法。
- 面對敵方戰術時較容易做出應變。

注意：能力不是直接轉換成固定經濟或固定勝率，而是影響相應事件發生的機率與執行結果。

# 四、隊伍特色與戰術風格

這是本次重要的擴充方向。

隊伍不能只有一個「前期隊」或「後期隊」標籤。

每支隊伍應該有多個可以同時存在的戰術特質。

## 4.1 隊伍特色

建議評估以下方向：

| 隊伍特質 | 主要影響 |
|---|---|
| 前期侵略 | 野區入侵、前期碰撞、Gank |
| 對線壓制 | 線上補刀、換血、線權 |
| 中野聯動 | 中路與打野協同、野區控制 |
| 後期運營 | 兵線管理、資源交換、經濟追回 |
| 團戰執行 | 團戰站位、集火、開戰與反打 |
| 資源控制 | 小龍、巴龍、地圖資源 |
| 分推運營 | 邊線壓力、兵線牽制 |
| 視野控制 | 插眼、排眼、資訊掌握 |
| 節奏轉換 | 順風擴大優勢、逆風尋找機會 |
| 逆風處理 | 落後時減少損失、尋找翻盤機會 |
| 順風營運 | 領先時控制地圖與結束比賽 |

上述特質不應該全部變成獨立手動設定欄位。

優先考慮由以下因素共同推導：

- 五名先發選手能力。
- 選手位置。
- 選手能力分布。
- 選手之間的相性。
- 教練能力。
- 長期形成的隊伍戰術習慣。

## 4.2 選手能力與隊伍特色的關係

例如：

一支隊伍擁有：
- 高對線上路。
- 高操作打野。
- 高對線、高意識中路。
- 普通下路。
- 普通輔助。

這支隊伍可能具有較強的上中野前期侵略能力。

但不能直接認定它一定會取得前期優勢。

還必須考慮：
- 打野是否擅長與線上配合。
- 中路是否能取得線權。
- 上路是否容易遭到針對。
- 輔助是否能支援野區。
- 對手是否擅長反制。
- 教練是否安排適合的戰術。

**個人能力決定能做什麼，隊伍協同性決定能不能一起做到。**

## 4.3 隊伍長期特色

隊伍特色不一定完全隨著選手更換而消失。

例如，一支長期擅長後期運營的隊伍，即使更換一名打野，仍可能保有原本的戰術習慣。

建議採用混合制：

- 選手能力：決定目前陣容的基礎能力與傾向。
- 隊伍戰術特色：代表長期形成的戰術習慣。
- 教練能力：影響戰術安排與臨場調整。

如果目前資料模型沒有隊伍戰術欄位，先提出最小幅度的擴充方案，不要直接大幅修改 Team Schema。

# 五、教練系統

沿用目前教練能力：

- draftStrategy
- metaAdaptation
- tacticalPlanning
- teamIntegration
- inGameLeadership
- playerDevelopment
- specialties

不同能力必須在不同環節產生效果。

| 能力 | 影響 |
|---|---|
| BP 策略 | 英雄選擇、Counter Pick、陣容組合 |
| 版本理解 | 版本強勢英雄與陣容理解 |
| 戰術規劃 | 前期戰術、中期轉線、資源安排 |
| 團隊整合 | 選手配合與團隊執行 |
| 臨場指揮 | 落後時的調整、關鍵決策 |
| 選手培育 | 長期成長，不直接影響單場能力 |

教練不能直接讓隊伍所有位置都取得優勢。

教練能力應該提高戰術選擇與執行品質，而不是直接增加全隊固定戰力。

# 六、BP 與英雄陣容系統

BP 是比賽中非常重要的決策環節。

不能只用一個 BP 分數決定優劣。

## 6.1 BP 必須考慮

1. 選手英雄熟練度（如果現有資料有提供）。
2. Counter Pick。
3. 版本強勢程度。
4. 五個位置的英雄組合。
5. 開戰能力。
6. 保排能力。
7. 前期強度。
8. 後期成長性。
9. 對線組合。
10. 團隊技能協同。
11. 陣容容錯率。
12. 教練 BP 能力。

如果目前專案尚未具備英雄資料、熟練度或版本資料，請先明確指出缺少哪些資料，不要自行假設已經存在。

## 6.2 BP 的取捨

BP 不應該讓每一路都拿到優勢。

例如：

| 位置 | GRX | BMG |
|---|---|---|
| TOP | 小優 | 小劣 |
| JG | 優勢 | 劣勢 |
| MID | 劣勢 | 優勢 |
| ADC | 均勢 | 均勢 |
| SUP | 優勢 | 劣勢 |

GRX 可能刻意犧牲中路，換取上中野以外的戰術優勢。

也可能選擇：
- 三路中只有一路 Counter。
- 犧牲對線換取團戰陣容。
- 前期弱勢但後期陣容完整。
- 選擇前期強勢英雄，爭取快速建立優勢。
- 選擇分推陣容，避免正面團戰。

BP 最後應該產生：
- 各路對線優劣。
- 整體陣容特性。
- 陣容強勢時間。
- 戰術方向。
- BP 主要取捨。
- BP 對實際比賽的影響。

不要把 BP 優勢直接當作整場勝率。

# 七、事件驅動比賽模擬

這是本次最重要的系統核心。

建議建立一套統一的 MatchEvent 資料結構。

實際名稱與欄位請依照現有專案架構設計，不要為了符合文件而強行採用不必要的 Schema。

## 7.1 事件類型

至少考慮：

### 擊殺事件
- First Blood
- Solo Kill
- Gank Kill
- Teamfight Kill
- Shutdown
- Assist
- Death

### 經濟事件
- Passive Income
- Lane Minion
- Jungle Monster
- Champion Kill Reward
- Assist Reward
- Tower Plate
- Tower Destruction
- Objective Reward（若遊戲規則存在對應獎勵）

### 地圖資源事件
- Dragon Kill
- Dragon Soul
- Baron Kill
- Elder Dragon
- Rift Herald
- Void Grubs
- Vision Placed
- Vision Destroyed

### 戰術事件
- Jungle Invade
- Gank Attempt
- Successful Gank
- Failed Gank
- Lane Pressure
- Tower Push
- Split Push
- Objective Contest
- Teamfight
- Retreat
- Resource Trade

### 比賽結束事件
- Nexus Destroyed
- Game End

不是每一場比賽都需要出現所有事件。

事件必須依照比賽時間、雙方能力、戰術、地圖狀態及隨機因素決定。

## 7.2 事件必須有前置條件

例如：

First Blood：
- 比賽開局雙方可能進行野區埋伏。
- 雙方有機會選擇入侵、守野或正常上線。
- 是否發生碰撞取決於雙方戰術與選手意識。
- 碰撞後才判定擊殺結果。

Gank：
- 打野必須有合理的路線與行動時間。
- 線上選手必須有可以配合的條件。
- 需要考慮線權、敵方視野與反蹲。
- Gank 可能成功、失敗，也可能被反蹲。

防禦塔：
- 必須有合理的兵線與推塔過程。
- 塔皮必須在有效時間與條件下取得。
- 防禦塔摧毀必須符合累積傷害條件。
- 不應該在比賽開始後極短時間內隨機出現塔被摧毀的事件。

小龍與巴龍：
- 必須符合物件刷新時間。
- 必須考慮隊伍是否有能力進行擊殺。
- 必須考慮視野、地圖位置、兵線及敵方干擾。
- 可能成功擊殺、被搶、放棄或交換其他資源。

## 7.3 事件不能只是一段敘事文字

每個事件都必須有實際效果。

例如：

一場三打三團戰：
- A 隊打野擊殺 B 隊 ADC。
- A 隊中路取得助攻。
- B 隊輔助死亡。
- A 隊打野獲得擊殺收入。
- A 隊中路取得助攻收入。
- B 隊輔助記錄死亡。
- 雙方選手更新傷害與 KDA。
- A 隊取得短暫人數優勢。
- A 隊趁機取得小龍。
- 更新隊伍經濟。
- 經濟曲線增加對應資料點。
- 比賽時間軸新增團戰及小龍事件。

事件必須同時更新所有相關資料。

# 八、經濟系統

## 8.1 經濟計算原則

雙方分別維護累積經濟。

經濟差：

主隊累積經濟 - 客隊累積經濟

經濟只能由合理的收入事件產生。

禁止：
- 每分鐘獨立隨機產生經濟差。
- 為了製造逆轉而直接修改經濟。
- 無事件原因的大幅經濟跳動。
- 讓曲線與選手個人經濟不一致。

## 8.2 經濟來源

至少考慮：

| 經濟來源 | 說明 |
|---|---|
| 被動收入 | 隨比賽時間累積 |
| 線上補刀 | 小兵死亡與補刀收入 |
| 野怪收入 | 擊殺野怪取得 |
| 擊殺收入 | 擊殺英雄取得 |
| 助攻收入 | 參與擊殺取得 |
| 塔皮收入 | 符合條件時取得 |
| 防禦塔收入 | 摧毀防禦塔取得 |
| 其他資源收入 | 依實際遊戲規則決定 |

注意：
- 小龍、巴龍等物件提供的戰略價值，不應全部直接轉換成經濟。
- 如果物件本身沒有直接經濟獎勵，應該透過增益、地圖控制及後續決策影響比賽。
- 所有經濟數值應集中管理，方便後續平衡。

## 8.3 經濟曲線

必須記錄：
- 比賽開始時間。
- 固定時間間隔的經濟快照。
- 重要事件發生時的經濟快照。
- 雙方累積經濟。
- 雙方經濟差。

固定間隔可以用於呈現穩定的時間軸，但事件發生時也必須保留精確時間點。

不要只記錄每五分鐘一次的資料，否則會失去團戰、擊殺及物件發生時的經濟變化。

## 8.4 經濟曲線視覺化

參考 LoL 職業賽事的 Gold Difference 圖。

- X 軸：比賽時間。
- Y 軸：經濟差。
- 主隊領先：正值。
- 客隊領先：負值。
- 0 軸：雙方經濟相同。

重要事件必須標記：
- First Blood
- 擊殺
- 防禦塔
- 小龍
- 龍魂
- 巴龍
- 遠古巨龍
- 重大團戰

點擊事件標記時，可以顯示事件詳情。

經濟曲線不得使用額外隨機數據。

# 九、選手個人數據

每位選手必須有自己的比賽統計。

至少包含：

| 數據 | 說明 |
|---|---|
| Kills | 擊殺 |
| Deaths | 死亡 |
| Assists | 助攻 |
| KDA | 擊殺、死亡、助攻綜合數據 |
| Damage Dealt | 對英雄造成傷害 |
| Damage Taken | 承受傷害 |
| Gold Earned | 累積經濟 |
| CS | 補刀數 |
| Vision Score | 視野分數 |
| Kill Participation | 擊殺參與率 |
| Damage Share | 團隊傷害占比 |
| Gold Share | 團隊經濟占比 |

如果部分數據目前無法合理模擬，先列出缺少的事件或資料，不要直接用隨機數字填滿。

## 9.1 個人數據一致性

- 五名選手的擊殺數總和，必須等於隊伍擊殺數。
- 五名選手的死亡數總和，必須等於對手擊殺數。
- 助攻數必須符合實際擊殺事件。
- 個人經濟必須能對應隊伍經濟。
- 傷害必須由實際戰鬥事件累積。
- CS 必須由補刀事件累積。
- KP% 必須根據實際擊殺與助攻計算。
- Damage% 必須根據實際傷害計算。

KDA 的除零處理應明確定義，不要產生 NaN 或 Infinity。

# 十、比賽時間軸

經濟曲線與時間軸必須共用同一份事件資料。

例如：

04:32
GRX Jungle 擊殺 BMG Top。

08:15
BMG 取得第一條小龍。

14:20
GRX 推掉下路外塔。

22:40
GRX 成功取得巴龍。

28:15

# 十一、比賽決策與隊伍風格互動

比賽不能只是按照固定時間觸發事件。

必須根據雙方當前狀態，決定接下來可能採取的行動。

例如：

## 前期侵略型隊伍

可能選擇：
- 野區入侵。
- 主動 Gank。
- 爭取線權。
- 提前控制河道。
- 主動爭奪小龍。

如果對線與中野聯動能力強，這些行動成功機率可能提高。

但如果線權不足、視野不足或敵方反蹲能力強，也可能失敗。

## 後期運營型隊伍

可能選擇：
- 避免不必要碰撞。
- 控制兵線。
- 交換地圖資源。
- 放棄不利團戰。
- 利用補刀與防禦塔收入縮小經濟差。
- 等待陣容強勢期。
- 透過視野控制準備大型物件。

這類隊伍即使前期落後，也可能逐漸追回經濟。

但不能讓運營能力直接產生固定經濟。

它應該透過更好的決策，讓隊伍取得合理的經濟機會。

## 團戰型隊伍

可能選擇：
- 主動集合爭奪物件。
- 利用陣容強勢期接團。
- 尋找敵方站位失誤。
- 利用開戰與反打能力創造機會。

## 分推型隊伍

可能選擇：
- 邊線牽制。
- 避免正面五打五。
- 利用人數交換取得地圖資源。
- 迫使對手分散防守。

不同風格必須互相影響，不應該存在固定的風格勝負公式。

# 十二、比賽階段與連續狀態

保留原本的前期、中期、後期設計。

但階段不能再直接代替整場比賽。

應該讓各階段影響：
- 戰術傾向。
- 行動選擇。
- 事件成功機率。
- 團戰能力。
- 資源決策。
- 失誤機率。

同時必須保留比賽連續狀態。

例如：
- 前期取得的經濟優勢會影響後續裝備與戰鬥能力。
- 中期取得的物件會影響後續資源爭奪。
- 選手死亡會影響短時間內的人數優勢。
- 防禦塔摧毀會改變地圖控制。
- 視野與兵線會影響下一次物件爭奪。

不能每個階段都重新獨立抽取戰力與結果。

---

# 十三、比賽勝負與結束條件

目前系統可能使用階段戰力差距決定勝者。

未來應逐步改為由比賽過程決定勝負。

優先考慮：
- 防禦塔與主堡狀態。
- 雙方兵線與地圖控制。
- 大型物件增益。
- 團戰結果。
- 選手存活狀態。
- 推進主堡的能力。

最終必須有合理的比賽結束事件。

例如：
- Nexus Destroyed。
- Game End。

不能只因為某一方的階段戰力比較高，就直接判定獲勝。

如果短期內還無法實作完整的地圖與主堡系統，請提出合理的分階段過渡方案，不要假裝已經具備完整遊戲模擬能力。

# 十五、資料一致性與驗證

這部分非常重要。

必須建立測試，避免圖表、事件與個人數據互相矛盾。

至少驗證：

1. 所有擊殺事件都能更新 KDA。
2. 選手擊殺總數與隊伍擊殺數一致。
3. 選手死亡總數與敵方擊殺數一致。
4. 經濟曲線與累積經濟一致。
5. 經濟變化能追溯至收入事件。
6. 時間軸與經濟曲線使用相同事件來源。
7. 小龍、巴龍等物件事件符合時間與重生條件。
8. 防禦塔事件符合推塔條件。
9. 比賽結束時間必須晚於所有比賽事件。
10. 系列賽勝負與單局結果一致。
11. 不允許 NaN、Infinity 或負數經濟。
12. 同一事件不得重複套用經濟效果。

另外需要進行大量模擬測試：

- 同 OVR、不同能力分布的隊伍。
- 前期侵略型對上後期運營型。
- 團戰型對上分推型。
- BP 強的教練對上 BP 弱的教練。
- 強隊對弱隊。
- 能力接近的隊伍。
- 不同隊伍風格的交叉測試。

檢查長期勝率、平均比賽時間、平均擊殺數、平均經濟差、物件控制率及爆冷比例。

不能只看單場結果。
